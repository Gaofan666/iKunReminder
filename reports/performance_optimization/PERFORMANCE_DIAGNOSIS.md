# PERFORMANCE_DIAGNOSIS —— iKunReminder 主界面空闲 CPU 诊断

> 本文所有结论都来自**本机实测**（Electron 44.3.0 / Windows 10.0.19045 / i5-1135G7 核显 Iris Xe / 8 逻辑核 / 主窗口 1179×840 CSS px、DPR=2 → 2358×1680 物理像素）。
> 未能实测的部分一律标注 **未验证**，不做推测性结论。

## 二、CPU 测试方法（可重复）

### 2.1 采样工具（已实现，可复用）

- **应用内**：启动参数 `--perf-sample --perf-label=<名> --perf-seconds=<秒> [--perf-ablate=<模式>]`
  - 用 **`app.getAppMetrics()`**（自带进程类型，GPU 不会被误算进 Renderer）每秒一行写入
    `reports/performance_optimization/raw/appmetrics-<label>-<时间>.csv`；
  - 字段：`label, iso, type, pid, percentCPU, idleWakeupsPerSecond, workingSetMB`
    （`percentCPU` 是"距上次调用"的区间占用，固定间隔连续调用即为区间值；`workingSetSize` 单位为 KB，已换算 MB）。
- **应用外**：PowerShell 读取全部 electron 进程的 **累计 CPU 秒**，在 15 秒窗口内取差值
  → `单核等效% = 100 × ΔCPU秒 / Δ墙钟秒`。这是本报告所有数字的口径（**单核等效百分比**，可能 >100%）。
- 说明：Windows 任务管理器的百分比是"占全机 CPU（8 逻辑核）的比例"，本报告数字 ÷8 才与之可比。

### 2.2 测试条件

启动后 10 秒预热（丢弃），随后 15~25 秒为采样窗口；每组重复 3 次取中位数（波动见第 4 节）；测试时关闭 DevTools 与其他录制。
测试使用**独立临时 userData**，不动用户数据。

### 2.3 消融开关（已实现，9 种）

`--perf-ablate=<模式>` → 往 `document.body` 加类，规则在 `style.css` 末尾：

| 模式 | 作用 |
| --- | --- |
| `grid-motion` | **暂停**网格运动（`animation-play-state:paused`，元素与静态外观保留） |
| `grid-hidden` | 隐藏网格 |
| `aurora-motion` | 暂停极光运动 |
| `aurora-hidden` | 隐藏极光 |
| `aurora-nofilter` | 保留运动与形状，**只去掉 `blur(10px)`** |
| `minor-motion` | 暂停 `.dot` / `.logo` |
| `all-motion` | 暂停全部装饰运动 |
| `canvas-hidden` | 隐藏角色舞台 |
| `minimal` | 隐藏全部装饰（网格/极光/点/logo/舞台） |
| `js-off` / `js-off-minimal` | **真正停掉页面 JS 循环**（清掉所有小整数 id 的 interval/timeout + 换掉 rAF）；后者再叠加 `minimal` |

> ⚠️ 刻意使用 `animation-play-state:paused` 而非 `animation:none`：后者会让元素回跳到第一帧，改变静态相位，测出的不只是"运动"的成本。
> 早期一次"关 CSS 动画无效"的实验**已作废**，但原因与被查明的不同：style.css 第 36-39 行本来就有 `body.anim-off *{animation-play-state:paused !important}`（全局有效），真正的失败原因是**消融类根本没有被加上**（驱动 bug），不是 CSS 规则失效。

| 测试版本 | 累计 CPU 总 | 与 baseline 差 | 说明 |

## 四、瓶颈排序（有证据）

**已被实测排除**（关掉后无任何变化）：

1. ❌ CSS 无限动画（网格 `background-position`、极光 `transform`+`blur`、`blink`、`logoSpin`）——暂停与隐藏均无变化；
2. ❌ 极光的 `filter: blur(10px)` 每帧重算 —— 去掉后无变化；
3. ❌ 页面 JS 循环（rAF + 250 ms tick + Canvas 更新）——**全部停掉后仍 ~175%**；
4. ❌ 装饰层的绘制/光栅化 —— 隐藏后不变。

**仍然可能（按怀疑度排序，均待进一步实测）**：

1. **窗口合成本身 / GPU 软件合成回退**（最可疑）：本机是 **核显 Iris Xe + 8 逻辑核**，而窗口是 **2358×1680 ≈ 4.0 Mpx**。若 Chromium 的回退到软件/CPU 合成（SwiftShader），那么"每帧把 4 Mpx 的面合成一次"本身就足以吃掉 100%+ 单核 —— 这与"关掉一切内容都没用"完全吻合。
   **验证方法（未执行，见 PERF_VALIDATION.md 第 5 节）**：读取 `app.getGPUFeatureStatus()` 看 `gpu_compositing` 是否为 `disabled_software`；或在 `chrome://gpu` 查看合成状态；或做一次 `contentTracing` 看有没有 `RasterTask`/软件合成事件。
2. **其他 BrowserWindow**：桌面宠物 / 日历挂件 / 气泡若在**隐藏状态下仍持续渲染**（`backgroundThrottling:false` 的副作用），会各自吃一份。实测中确实观察到 1 个 ~134 MB 的进程稳定吃 12.8%（**未验证**它属于哪个窗口）。
3. **主窗口 renderer 的常驻内存 700~850 MB**：与上面的合成/光栅开销可能同源（大图层缓存），**未验证**因果。

| 历史推测 | 结论 |

## 7.3 本轮能下的结论

**开销集中在 GPU 进程，而且与页面内容、动画、窗口像素量都无关**（在 1179×840 默认窗口下恒为 ~135~150%）。
这更像"**这台机器（i5-1135G7 核显 + Win10）上 Electron 窗口合成本身存在一条恒定开销**"，
而不是本项目某个动画写法的问题。

**下一步必须先做的对照实验**：同一台机器、同样的量法，跑一个**最小 Electron 应用（纯白页，无任何动画）**。
- 若它的 GPU 也是 ~140% → 确认为环境/驱动基线，本项目无论怎么改都降不下来（应转向别的方向：例如减少窗口、或换渲染方式）；
- 若它接近 0% → 说明仍是我们这边某个**没被消融覆盖到**的东西（候选：主窗口的某个持续存在的图层/滤镜组合、`backgroundThrottling:false` 的持续合成），继续二分。

（本轮我尝试过这个对照实验，但控制组进程未被捕获，**未取得有效数据**。）

# 八、突破：动画的「组合效应」（同一进程内 A/B，决定性证据）

| 状态 | 应用总 CPU（单核等效） |
| --- | ---: |
| ① 原样 | **143.7 %** |
| ② 4 个 CSS 动画全部 `paused` + 画布 `hidden` + 页面所有 `setInterval`/rAF 停掉 | **0.7 %** |

（② 的执行结果已就地验证：`正在运行的动画 = []`，`.grid-floor/.aurora/.dot` 的 `animation-play-state` 均为 `paused`。）

而**单独**暂停某一个动画只省 0~14 点：grid 9.6 / aurora 0.8 / minor −1.6 / all 13.6 / aurora 去滤镜 −5.6。
**对照实验**（纯白页 Electron、同窗口尺寸、同样量法）= **0.2 %** → 排除"环境/驱动基线"。

## 8.1 由此得到的机制

**只要还有任意一个动画在跑，窗口的合成器就会持续出帧**；而**每帧的成本正比于窗口面积**。
两件事必须同时成立才会出现 ~140%：
- **动画提供"帧"**（所以单独关掉一个没用 —— 剩下的动画照样让它出帧）；
- **窗口面积提供"每帧的代价"**（主窗口 2358×1680 ≈ 4.0 Mpx，且 DPR=2）。

这也解释了其它所有观测：全静止 → 不再出帧 → 0.7%；纯白页 → 从不出帧 → 0.2%。

## 8.2 为什么右下角的小桌宠很省？

它是**独立的小窗口**（约 0.15~0.25 Mpx，比主窗口 4.0 Mpx 小约 20 倍），
所以**即使它一直在动，每帧要合成的面积也小得多** → 占用自然低。
这不矛盾，恰恰是上面机制的正面印证。

## 8.3 更正：一次被判为无效的实验

`--diag-win=600x400` 那轮"窗口缩小 16 倍、GPU 无变化"的结论**不可靠** ——
`--diag-win` 属于自检模块，自检跑完会**还原窗口尺寸**（代码里就有还原逻辑），
所以测量时窗口很可能已经回到 1179×840。**该结果作废**，不能作为"与面积无关"的证据。

## 8.4 优化方向（尚未实施）

1. **减少每帧的像素量**：把装饰背景（网格 / 极光）按更低分辨率渲染再放大 ——
   它们本身是柔和/模糊的，**视觉损失可忽略**，却是最直接的每帧成本削减；
2. **让持续出帧的必要性下降**：用合成器友好的写法（`transform`/`opacity` 动画、图层提升），
   但**不能**用"降低帧率/停掉动画"这类损失观感的做法；
3. 两条都要在**保持视觉一致**的前提下做，并按任务书要求做视觉回归对比。
